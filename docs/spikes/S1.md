# Spike S1: phone → Relay → Back Office with a pinned office key

Issue #32. Date: 2026-11-13. Code: `spikes/s1/` (throwaway; its own Go
module and Xcode project).

## Verdict: **Yes, with one required change**

An iPhone app can reach its Back Office through a relay using HTTP `CONNECT`
(iOS 17 `ProxyConfiguration`), spliced onto an SSH channel the office opened
outbound, with TLS 1.3 end to end to a pinned office key. The relay sees only
ciphertext.

**Required change:** default App Transport Security (ATS) will not accept the
office's self-signed certificate, even when the app pins it and anchors trust
to it. V1 needs one narrowly scoped ATS exception for the reserved
`*.wehelp.invalid` office names (details below). This replaces the plan's
"no ATS exception" assumption.

## What was built

| Piece | What it does |
|---|---|
| `s1 relay` | SSH listener (offices, `golang.org/x/crypto/ssh`, one registered ed25519 key standing in for the Registry list) plus a TLS 1.3 `CONNECT` listener (phones). On `CONNECT office-1.wehelp.invalid:443` it opens a `wehelp-conn` SSH channel to that office and splices bytes. It records every spliced byte for the plaintext check. |
| `s1 office` | Dials the relay outbound, pins the relay's SSH host key, accepts only `wehelp-conn` channels, terminates TLS 1.3 with the office key, and reverse-proxies to `wehelpd`. Reconnects with backoff. |
| `S1Spike` iOS app | URLSession with `ProxyConfiguration(httpCONNECTProxy:tlsOptions:)`. The relay hop is pinned in an `NWProtocolTLS` verify block; the office hop is pinned in the `URLSession` delegate. Pin = base64 SHA-256 of the key's X9.63 bytes. |

## Results

**Simulator** (iPhone 17 Pro, iOS 27) → relay on the dev laptop → office on the laptop → local `wehelpd`:

| Check | Result |
|---|---|
| Correct relay and office pins | **HTTP 200 `{"message":"pong"}` in 198 ms** |
| Wrong office pin (a relay or attacker presenting another key) | Refused (`-999`, cancelled by the pin check) |
| Wrong relay pin (unknown relay) | Refused (`-1202`) |
| Unknown office ID | Relay answers `CONNECT` with 502 |
| Relay recordings (16 files, 8 connections, both directions) | **No plaintext**: no marker header, no `/api/v1` path, no response body. First bytes are a TLS record (`16 03 01`). The only readable string is the office hostname in the TLS ClientHello, which the relay already knows from `CONNECT`, and which is inside the outer TLS to the relay, so the network can't see it. |

**curl** through the same path also returned 200, and its marker header was absent from the recordings.

## Findings

1. **ATS rejects pinned self-signed certificates.**
   - URLSession's delegate approved the pinned key and returned
     `.useCredential`. CFNetwork still ran its own system trust check and
     failed: `Trust evaluate failure: [leaf AnchorTrusted]`, then
     `ATS failed system trust` and `-1200`.
   - Calling `SecTrustSetAnchorCertificates` on the challenge's trust (anchored
     to the pinned leaf) did **not** change that. ATS evaluates trust
     independently.
   - **What works:** an ATS exception for `wehelp.invalid` with
     `NSIncludesSubdomains` and `NSExceptionAllowsInsecureHTTPLoads`, keeping
     `NSExceptionMinimumTLSVersion: TLSv1.3`.
   - **Why it's acceptable:**
     - `.invalid` is reserved (RFC 2606) and resolves nowhere, so these names
       are reachable only through the pinned relay;
     - every connection is still pinned by the delegate, which fails closed;
     - TLS 1.3 stays required;
     - no other domain is affected.
   - **Audit note:** the exception and its reasoning must be listed in the
     MASVS checklist (#44).
   - **Alternatives considered:** a public CA certificate per office (needs a
     domain and DNS per office, against the QR-pairing design), installing a
     CA profile on patients' phones (unacceptable UX), or doing the inner TLS
     with Network.framework instead of URLSession (Network.framework isn't
     subject to ATS, but we'd lose URLSession's HTTP stack). A V1-M2 PR could
     revisit Network.framework if the exception is challenged in audit.
2. **Swift 6 isolation.**
   - The `sec_protocol_options_set_verify_block` closure crashed the app with
     "Block was expected to execute on queue main-thread" when it was written
     inside a SwiftUI view: it inherited main-actor isolation and then ran on
     a background queue.
   - Build it in a `nonisolated` helper. The real `APIClient` must do the same.
3. **macOS Local Network privacy on Barnacle (demo topology only).**
   - On Barnacle (macOS 27), a non-Apple program reaching a LAN address needs
     the user's one-time "Allow local network" approval:
     - **Under launchd:** `connect: no route to host`.
     - **Started over SSH:** the connection works while the SSH session lasts,
       then every write fails with `broken pipe` once it ends.
     - **In a container:** traffic leaves through Colima's VM process, which
       gets `connection refused`.
   - Apple's own tools (for example `bash`) are exempt, which made it look
     like a code bug at first.
   - **Impact:** none in production, where the Relay is on the internet and
     the rule only covers LAN destinations. In the Demo topology (the Relay
     on the laptop on the LAN), approve Local Network once on Barnacle for
     Colima or the office binary. This is added to docs/APPLIANCE.md.
   - The office path through Barnacle was therefore not shown in this spike.
     The relay, SSH channel and TLS mechanics were shown with the office on
     the laptop. Re-run the Barnacle leg after the approval.
4. **Operational details for V1-M2:**
   - The relay must speak HTTP/1.1 only on the `CONNECT` listener, so the
     connection can be hijacked.
   - Bytes already buffered by the HTTP server must be forwarded first.
   - Pins of the raw X9.63 key are simplest on iOS (`SecKeyCopyExternalRepresentation`).
   - Keep SNI as the office host, so one relay certificate serves all offices.

## Recommendation for V1-M2

Go ahead with SSH + `CONNECT` + pinned office key, as designed. Update #36: the
app keeps the scoped `*.wehelp.invalid` ATS exception instead of "no ATS
exception", builds its TLS verify blocks outside actors, and fails closed on
both pins. Not yet shown, to cover in V1-M2: a physical iPhone, the Barnacle
leg after Local Network approval, reconnect under load, and many concurrent
channels.

## How to rerun

```
cd spikes/s1 && go build -o s1 . && ./s1 keys -dir keys -relay-ip <laptop-ip>
./s1 relay -dir keys -ssh 0.0.0.0:2222 -connect 0.0.0.0:8443 -dump dumps
./s1 office -dir keys -relay 127.0.0.1:2222 -upstream http://127.0.0.1:8080
cd ios && xcodegen generate   # set the two pins printed by `s1 keys` in S1SpikeApp.swift, run in a simulator
```
