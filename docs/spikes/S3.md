# Spike S3: push notifications sent from the Relay

Issue #34. Date: 2026-11-13. Code: `spikes/s3/` (throwaway; its own Go
module and Xcode project).

## Verdict: **Yes**

A Go program standing in for the Relay sent pushes through Apple's APNs
sandbox using the team's token-based auth key, and an iOS app received and
displayed them. Only fixed, PHI-free categories can be sent.

## What was built

| Piece | What it does |
|---|---|
| `spikes/s3` (Go) | Sender using `sideshow/apns2` with token (`.p8`) auth. It accepts only three categories (`new_message`, `appointment_reminder`, `visit_starting`), each mapped to fixed generic text, and refuses anything else before contacting Apple. The key is read from disk and never printed. |
| `spikes/s3/ios` (S3Spike) | Requests notification permission, registers for remote notifications, shows its device token, and lists pushes received in the foreground. `aps-environment: development`. |

## Results

Simulator (iPhone 17 Pro, iOS 27, Apple silicon). Simulators receive real
APNs sandbox pushes, so no device was needed for this spike.

| Check | Result |
|---|---|
| Push entitlement and device token | Provisioned automatically with `-allowProvisioningUpdates`; the app received a real sandbox token |
| `new_message`, `appointment_reminder`, `visit_starting` | **HTTP 200** from APNs in 219–315 ms. All three were shown on the device with generic text only, plus the category |
| Disallowed category (`lab_results_ready`) | Refused by the sender before contacting Apple |
| What leaves our systems | Device token + category + fixed text. No names, times, message text or record IDs |

## Findings

1. **The auth key is scoped, which is good.**
   - Key `WBC2TGU95K` was created **for one app ID (`com.zacelston.wehelp`)
     and the sandbox environment only**. Apple enforced both:
     - another bundle ID got `TopicDisallowed`;
     - the production host got `BadEnvironmentKeyInToken`.
   - Keep keys scoped like this. For V1:
     - production needs a production-enabled key, held only on the Relay;
     - the provider app (#69), if it's a separate app, needs its topic added
       or its own key.
2. **`sideshow/apns2` works, but its dependencies are stale.**
   - The latest release is v0.25.0 (Oct 2024). It pins a 2022
     `golang.org/x/net` with known vulnerabilities (govulncheck), plus
     `golang-jwt/jwt/v4`.
   - Bumping `golang.org/x/net` to v0.62.0 in our `go.mod` cleared those.
   - V1 options: adopt it with dependency overrides and govulncheck in CI
     (#43), or hand-roll the ~100 lines it takes (an HTTP/2 POST plus an
     ES256 JWT). Prefer hand-rolling unless it grows.
3. **The local Go toolchain is unpatched.** govulncheck flagged Go 1.26.0
   standard-library vulnerabilities (`net/http`, `crypto/x509`), fixed in
   later 1.26 patch releases. This affects the main server too. Pin a patched
   toolchain in `go.mod` and CI (#43).
4. **Swift 6:** `userNotificationCenter(_:willPresent:)` must be
   `nonisolated` in a main-actor app delegate. Copy plain values out before
   hopping to the main actor.
5. **Push needs no Back Office internet access beyond the Relay.** The Back
   Office sends (device token, category) over its SSH channel; only the
   Relay talks to Apple.

## Recommendation for V1-M3 (#7)

Send pushes from the Relay as designed, with the category allow-list
enforced on the Relay. Store device tokens on the Relay per office; the
Back Office learns a token only to ask for a push. Treat `Unregistered` or
`BadDeviceToken` responses as a signal to remove the token. Use a
production-scoped key for the field deployment.

## How to rerun

```
cd spikes/s3 && go build -o s3 .
cd ios && xcodegen generate   # build with -allowProvisioningUpdates; run on a simulator; allow notifications
./s3 -key <AuthKey.p8> -key-id <id> -team <team> -topic <bundle id> -token <device token> -category new_message
```
