# Spike A1: Android through the Relay, with a Keystore device key

Issue #127. Date: 2026-11-16. Code: `android/spike/`. It's a throwaway
app, not the product app (#128).

## Verdict: **Yes, on the emulator. The physical phone is still to run**

An Android app reaches a Back Office through the Relay with both pins
failing closed, and pairs with a real staff-web QR. The Back Office accepts
an Android Keystore P-256 key and its signatures unchanged.

**Still to do:** the run on a Samsung Galaxy S24 is the one that shows a
hardware-backed key (StrongBox or TEE). The emulator only has software keys.

## What was built

| Piece | What it does |
|---|---|
| `Pins.kt` | The WeHelp pin: base64 SHA-256 of the **uncompressed X9.63 point** (`04 ‖ X ‖ Y`, each coordinate padded to 32 bytes). A `PinTrustManager` checks the leaf's key against it and ignores the system trust store, names and dates. It's a plain `X509TrustManager`, so Conscrypt does no hostname check. |
| `Tunnel.kt` | TCP to the Relay → `SSLSocket` (TLS 1.3 only, Relay pin) → `CONNECT <office>.wehelp.invalid:443` → a second `SSLSocket` layered on the first with `createSocket(socket, host, 443, true)` (TLS 1.3, SNI set to the office host, office pin). Then a minimal HTTP/1.1 client: `Connection: close`, `Content-Length` or chunked bodies. |
| `DeviceKey.kt` | P-256 in `AndroidKeyStore`: `PURPOSE_SIGN`, SHA-256, StrongBox first, and without it on `StrongBoxUnavailableException`. Reports `KeyInfo.securityLevel`. The public key is sent as DER SPKI, and proofs are `SHA256withECDSA` (DER). |
| `MainActivity.kt` | Scans the pairing QR (Google code scanner) or takes it as an intent extra, then: pair → `GET /me` → refresh with a proof → `GET /me` → a wrong Relay pin → a wrong office pin → sign out. It logs PASS or FAIL for each step to logcat (`WeHelpSpike`) and never logs the invite or tokens. |

There are no networking dependencies: the platform's `SSLSocket`
(Conscrypt), `org.json` and the Keystore. The only library is
`play-services-code-scanner`, for the QR (see the lit review).

## Results

**Emulator** (Android 15, API 35, Google Play x86_64 image, headless with
KVM on MiniZ) → Barnacle's Relay (`192.168.1.2:9443`) → Barnacle's Demo
Clinic office. The pairing payload was a real staff-web **Pair phone** QR
for a demo patient.

| Step | Result | Time |
|---|---|---|
| Key is not exportable | PASS | |
| Key is hardware-backed | **software** (expected on an emulator; MOBILE_CLIENT.md allows it in debug builds only) | |
| `POST /pairing/redeem` with a `pair` proof | 200, paired as patient | 1400 ms |
| `GET /me` | 200 | 311 ms |
| `POST /auth/refresh` with a `refresh` proof | 200 | 797 ms |
| `GET /me` with the new token | 200 | 766 ms |
| Wrong Relay pin | fails as a **relay** pin mismatch | |
| Wrong office pin | fails as an **office** pin mismatch | |
| `POST /auth/logout` | the device was revoked in the Back Office (checked in its database), but the client hung reading the `204` (see below; fixed) | |

**Times** are for a fresh tunnel and two TLS handshakes per request. The
product app should keep one office connection alive (OkHttp, below) rather
than reconnect per call.

**The Relay sees ciphertext only.** Its log has one line per phone
connection: the office ID, bytes up and down, and duration. There's no host,
path or content. The wrong-Relay-pin attempt never reached `CONNECT`.

**Physical phone:** _Samsung Galaxy S24, to run with Wireless debugging from
MiniZ. Record `KeyInfo.securityLevel` (StrongBox from Knox Vault is
expected) and what the code does without StrongBox._

## Findings

1. **Pins: don't use OkHttp's `CertificatePinner` or network-security-config
   `<pin-set>`.** Both hash the whole SubjectPublicKeyInfo, which is a
   different value from WeHelp's X9.63 pin. Each would reject every office.
   Use a trust manager that computes the X9.63 hash, as `Pins.kt` does. A
   unit test checks the encoding against the last 65 bytes of the SPKI
   (padding included).
2. **The layered-socket approach works on Conscrypt.** It uses TLS 1.3 on
   both hops, SNI on the inner hop, and a pinned trust manager on each.
3. **Never read a body "until close" through the tunnel.** Logout answers
   `204` with no body. The first version read until EOF and hung for the 20 s
   socket timeout, and the Relay log shows that connection open for 20.27 s.
   The Relay does pass a close through (`splice` calls `CloseWrite` towards
   the phone when the office's channel ends), so either the office doesn't
   end its channel after a `Connection: close` reply, or Conscrypt doesn't
   surface the layered close as EOF. Bodies are now read only by
   `Content-Length` or chunking, and `204`/`304` have none. The product
   client (OkHttp) already behaves this way. Investigating the close is a
   small follow-up; it doesn't block Android.
4. **The device key works unchanged.** `KeyPairGenerator("EC",
   "AndroidKeyStore")` with `secp256r1` gives a DER SPKI that
   `auth.ParseDevicePublicKey` accepts. `SHA256withECDSA` gives DER
   signatures that `auth.VerifyDeviceProof` accepts for both `pair` and
   `refresh`. No server change is needed.
5. **Minimum Android version: 10 (API 29).** TLS 1.3 is on by default from
   Android 10, and `setIsStrongBoxBacked` is API 28. `KeyInfo.securityLevel`
   is API 31; below that the app only gets `isInsideSecureHardware`. #129
   can raise the minimum to 12 (API 31) if it wants the exact level.
6. **The QR scanner.** Google's code scanner needs no camera permission and
   draws its own UI, but it needs Google Play services. Phones without them
   (some de-Googled builds, some markets) would need ZXing, or CameraX with
   ML Kit's bundled model. It's a #130 decision; a Samsung has Play
   services.

## For the product app (#128–#130)

- **OkHttp is fine for the office hop if the Relay hop is done by hand:**
  - a custom `SocketFactory` returns a socket already through the pinned
    Relay TLS and `CONNECT`;
  - OkHttp's `sslSocketFactory` and trust manager do the office pin;
  - a `HostnameVerifier` accepts only the `<office>.wehelp.invalid` host,
    since the pin is the identity.

  That gives connection reuse instead of a tunnel per request. Try it in
  #128; if OkHttp's assumptions about plain sockets get in the way, keep
  this spike's client with keep-alive.
- **Keys:** refuse `software` outside debug builds (#129). Per account,
  alias the key as `wehelp-device-<office>-<user>`.
- **Nothing on disk:** `allowBackup=false` is already set here; data
  extraction rules come in #129.

## How to run it

On MiniZ (`~/android/sdk`, JDK 21; `source ~/.profile`):
```
cd ~/spike && ./gradlew testDebugUnitTest assembleDebug
emulator -avd spike -no-window -no-audio -gpu swiftshader_indirect &   # or a phone over Wireless debugging
adb install -r app/build/outputs/apk/debug/app-debug.apk
```
Then press **Scan pairing QR** in the app. On an emulator, decode a saved QR
image on the Mac with `zbarimg --raw` and pass it with
`adb shell am start -n com.wehelp.spike/.MainActivity --es payload_b64 <base64>`.
Results: `adb logcat -s WeHelpSpike`.
